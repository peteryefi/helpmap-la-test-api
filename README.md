# Helpmap Reports API

Shared backend for browser-submitted disaster reports (Data Flow 1 of the
Helpmap testbed). Replaces the original "browser-local, localStorage-only"
design: reports submitted by any user are now persisted server-side and
visible to every user, including after a page refresh.

Two endpoints:

- `POST /reports` — submit a report
- `GET /reports` — list reports from the last `REPORT_WINDOW_HOURS`
  (default 24h — see "Report window" below), newest first

Plus `GET /health` for a trivial uptime check.

## Report format

Mirrors the frontend's mock report shape exactly, so the PWA can consume
API responses with no adapter code:

```json
{
  "id": "mock-1",
  "description": "Fire in the park.",
  "photoUrl": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
  "latitude": 34.090599,
  "longitude": -118.2468,
  "createdAt": "2026-08-11T17:00:00.000Z",
  "type": "Fire"
}
```

Notes:

- `id` and `createdAt` are optional on submit — the server fills in a UUID
  and the current UTC time if omitted. If you *do* send an `id` that
  already exists, the API returns `409 Conflict` rather than silently
  overwriting the existing report.
- `type` is currently accepted as free text, not a strict enum, because the
  full `ReportType` list wasn't confirmed at build time (only `Fire` was
  shown). Once you have the complete list, tightening `app/schemas.py` and
  `app/models.py` to a proper enum is a ~10-minute change.
- `photoUrl` is optional (nullable). For this testbed it holds a
  **base64-encoded image**, not a hosted URL, despite the name (kept as
  `photoUrl` to match the frontend field exactly). Either a raw base64
  string or a full data URI (`data:image/jpeg;base64,...`) is accepted and
  stored as-is. Capped at `MAX_PHOTO_BASE64_CHARS` in `app/config.py`
  (default 8,000,000 characters ≈ 6MB of image data) — a request over that
  gets a `422`. **If you deploy behind nginx** (see below), its default
  1MB body limit will reject large photos before they even reach the API;
  `deploy/nginx.conf` raises this to 10MB to match.

## Running locally

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
uvicorn app.main:app --reload
```

API docs (auto-generated by FastAPI): http://localhost:8000/docs

Run tests: `pytest`

## Rate limiting

No authentication on this API (per your call — just endpoints + limits for
the testbed). Rate limits are per client IP via `slowapi`:

- `POST /reports`: 15/minute (default, in `.env`)
- `GET /reports`: 60/minute

This is aimed at the actual concern you flagged — someone mashing "submit"
and creating duplicate reports — not a hostile attacker. One thing to know
going in: if the demo happens on one venue Wi-Fi network, multiple
attendees can share a single public IP address (NAT), so the limiter
throttles everyone behind that IP together, not just one person. The
defaults above are set generously to tolerate a room of ~50 people on
shared Wi-Fi; if real testing shows legitimate submissions getting
`429 Too Many Requests`, raise `RATE_LIMIT_SUBMIT` / `RATE_LIMIT_LIST` in
`.env` and restart the service — no code change needed.

## Report window

`GET /reports` only returns reports created within the last
`REPORT_WINDOW_HOURS` hours (`app/config.py`, default **24**). This is a
fixed server-side window, not a query parameter, so every client sees the
same cutoff.

Common values, all one line to change in `app/config.py` (or `.env`):
`24` (1 day), `48` (2 days), `96` (4 days), `168` (1 week).

24h is the default because the sprint plan has real testing running
Tue Aug 26 – Fri Aug 29, and the Sat Aug 30 demo should show fresh activity
rather than four days of accumulated test submissions. **If you'd rather
the demo show everything submitted across the whole sprint, change this to
168 before Saturday.**

One caveat: the window filters on `createdAt`, and a client is allowed to
supply its own `createdAt` on submit (see "Report format" above). A
report submitted with a backdated timestamp will age out of the window
early; this isn't enforced against tampering, since there's no auth on
this API regardless.

## Deploying to AWS (Lightsail)

Recommended over Lambda for this specific piece: Lambda's filesystem is
ephemeral and concurrent invocations can land on separate execution
environments, so SQLite on Lambda would not reliably give you "every user
sees every report" — the one requirement this whole rebuild exists to
satisfy. A single persistent Lightsail instance with SQLite on local disk
avoids that problem entirely, at demo scale.

1. **Create the instance**: Lightsail console → Create instance → Linux/Unix
   → OS Only → Ubuntu 22.04 → smallest plan ($5/mo tier is plenty for this
   load) → attach a static IP.
2. **Open ports**: in the instance's Networking tab, allow HTTP (80),
   HTTPS (443), and SSH (22, restrict to your IP if possible).
3. **DNS**: point a subdomain (e.g. `api.helpmap.example`) at the static IP
   via Route 53 (see the main architecture memo, Section 3.4 — domain/DNS
   ownership needs confirming regardless).
4. **First-time setup**, SSH'd into the instance:
   ```bash
   sudo apt update && sudo apt install -y python3-venv python3-pip nginx certbot python3-certbot-nginx git
   ```
5. **Deploy the app**: copy `deploy/deploy.sh` to the instance (or clone the
   repo, which includes it) and run it — it clones/pulls, sets up the
   venv, installs deps, creates `.env` from the example, installs the
   systemd service, and starts it.
   ```bash
   bash deploy/deploy.sh
   ```
6. **Edit `.env` on the instance**: set `CORS_ORIGINS` to the real Amplify
   URL once the PWA is deployed, then `sudo systemctl restart helpmap-api`.
7. **nginx + TLS**: copy `deploy/nginx.conf` into
   `/etc/nginx/sites-available/helpmap-api`, symlink it into
   `sites-enabled`, reload nginx, then run
   `sudo certbot --nginx -d api.helpmap.example`. This is not optional —
   the PWA is served over HTTPS from Amplify, and browsers block a plain
   HTTP `fetch()` from an HTTPS page (mixed content), so the API needs a
   real TLS cert, not just an IP address.

After that, `GET https://api.helpmap.example/health` should return
`{"status": "ok"}`, and `https://api.helpmap.example/docs` gives you an
interactive Swagger UI to test both endpoints by hand.

### Redeploying

SSH in and rerun `bash deploy/deploy.sh` — it pulls the latest code,
reinstalls dependencies if `requirements.txt` changed, and restarts the
service. The SQLite file in `data/` is untouched by a redeploy.

## Known limitations (by design, for a testbed)

- Single instance, single disk: this is not built to survive an instance
  failure. Acceptable for a one-day demo; would need Postgres + a proper
  managed DB before any production use.
- No authentication: anyone with the URL can submit or read reports. Fine
  for a controlled demo audience; not appropriate beyond that.
- `type` isn't validated against a fixed list yet — see "Report format"
  above.
- Photos are stored as base64 text directly in SQLite rows. Fine at demo
  volume/duration; if usage grows, move to storing photos in S3 and keep
  only a URL in the DB.
